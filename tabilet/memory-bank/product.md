`browsertools` is a Go-first tooling project for producing reviewed UWS
browser capability profiles from real website UI evidence. Its job is to make
browser-based automation reviewable and portable without turning UWS into a
general browser automation language.

The product boundary is:

```text
real website UI
  -> browsertools using Playwright / llm-scraper / Crawl4AI / Firecrawl
  -> reviewed browser-profile
  -> UWS operation binds to browser-profile action
```

## Users

- OpenUdon maintainers who need a reviewed browser-profile artifact when no
  sufficient API source document exists.
- Runtime maintainers who need stable, validated profile fixtures and
  revalidation evidence before executing browser actions.
- Reviewers who need to inspect learned UI capabilities, locators, outputs,
  side effects, confidence, evidence, expiry, and origin allowlists.
- Tooling agents that can propose profile drafts from browser sessions, crawler
  results, or structured extraction libraries.

## Core Concepts

- **Browser profile**: a UWS `browser-profile` source document conforming to a
  pinned UWS browser 1.5 through 1.10 schema. It records reviewed UI
  capabilities, not browser command traces, and Browsertools emits the oldest
  sufficient version.
- **Browser content-trust resolver**: an explicit adapter from reviewed browser
  profiles to UWS 1.9.1 advisory operation contracts. It identifies data,
  instruction, and authority-bearing input channels and treats browser-derived
  outputs as untrusted while classifying their free-text, constrained-scalar,
  composite, or unknown capability separately. It does not run during ordinary
  profile validation or browser execution.
- **Browser authentication profile**: a package-local
  `uws.browser-authentication.1.0` sign-in recipe with exact origins,
  accessibility locators, symbolic credential slots, an explicit MFA
  alternative, and a success condition. It contains no credential or session
  values and is not registry-published in this release.
- **Browser registration profile**: a package-local
  `uws.browser-registration.1.0` account-creation recipe with exact origins,
  symbolic identifier/password slots, exactly one explicitly confirmed
  submit, fixed human-checkpoint kinds, and a value-free success condition.
  Browsertools validates, drafts, and digest-reviews it offline; registration
  execution and account state remain downstream.
- **No-submit registration authoring**: a separate
  `browsertools.registration-author-session.v1` observation protocol producing
  one private `browsertools.registration-authoring.v1` BRP candidate. It is
  exact-origin and GET/HEAD-only, carries no authentication/session or mutation
  authority, and reuses the existing registration-review v1 contract. The
  authenticated author-session/result v2 wires remain unchanged.
- **Query-safe registration authoring v2**: additive
  `browsertools.registration-author-session.v2` and
  `browsertools.registration-authoring.v2` contracts retain explicitly
  reviewed canonical literal structural queries while registration v1 remains
  byte-exact and query-free. Query material never enters reduced observations,
  diagnostics, logs, filenames, or result paths.
- **Guarded registration observation**: one explicitly constructed headed,
  sandbox-required ephemeral Chromium adapter implements that no-submit
  interface with exact-origin GET/HEAD routing, bounded ARIA-only reduction,
  no input/click/value/state API, and fail-closed teardown.
- **Explicit registration candidate construction**: a browser-independent
  builder binds one current reduced generation to a complete operator-authored
  registration spec, exact submit/review selections, approved origins, and
  fixed call-safety choices. Missing profile or cleanup decisions fail rather
  than being inferred from the page.
- **Private registration finalization**: after clean browser teardown, one
  finalize operation independently reconstructs, strictly decodes, creates,
  reopens, and revalidates the exact owner-only result. Its location remains an
  in-process value and never becomes profile or result content.
- **Isolated registration-author worker**: the standalone CLI and re-executing
  OpenUdon parent use one importable entry that preflights the installed driver,
  owns closeable NDJSON input and Chromium teardown, and finalizes only under
  an owner-only private root. It returns no path or digest and exposes no
  Playwright handle; the parent owns its minimal environment, stable executable
  image, and process group.
- **Assisted authentication observation**: an explicitly selected headed
  authoring run against an existing authentication profile. A human completes
  credential, submit, and MFA steps in a fresh browser context while
  Browsertools retains only exact origins, declared paths, match counts, and
  bounded POST counts.
- **Authenticated goal authoring**: an explicitly selected Chromium session
  that remains alive across human credential/MFA entry and post-login
  exploration. Browsertools owns the context and exposes only reduced,
  disclosure-gated semantic candidates; no session material crosses the
  process boundary.
- **Reviewed MFA/output authoring**: author-session v2 shows only compatible
  checkpoint kinds for an exact human choice and accepts at most 16 reviewed
  accessibility outputs from the final observation. Output proofs carry no
  page values and may use only canonical exact names or a currently unique
  role.
- **Settled author-session navigation**: an approved navigation-producing
  click is complete only after its current page or reviewed popup has settled
  and been reconciled into the portable context inventory. Headed child
  processes receive only display/session-bus environment needed by Playwright,
  never credential or provider variables.
- **Importable author-session worker**: the Browsertools-owned process entry
  used by both the standalone CLI and iCoT's hidden re-executed worker. It
  accepts only context, private root, optional driver directory, stdin, and
  stdout; browser/session ownership remains in that worker process.
- **Goal predicate**: a typed, value-free condition over approved origin,
  clean path, context, and uniquely matched accessible presence. Promotion
  requires both predicate satisfaction and human completion confirmation.
- **Portable browser context**: the additive UWS browser 1.6/authentication
  1.1 description of one exact popup or frame relationship. The implicit
  `main` context keeps every browser 1.5/authentication 1.0 profile compatible.
- **Capability action**: a named UI capability under `actions`, selected by a
  UWS operation's `sourceOperationId` or `sourceOperationRef`.
- **Observation evidence**: accessibility snapshots, DOM text, structured data
  discovery, crawler output, screenshot/OCR hints, successful probes, and human
  notes used to justify a profile draft.
- **Adapter**: a bounded importer for output from a tool such as Playwright,
  llm-scraper, Crawl4AI, or Firecrawl. Adapters normalize evidence; they do not
  make the evidence trusted. Extraction results without a portable source are
  unbound hints and cannot auto-promote.
- **Authoring acquisition**: an explicitly selected, origin-bounded browser
  session that gathers untrusted evidence into a private boundary. It is not
  production execution and does not make browser mechanics portable.
- **Private rich evidence**: an explicitly selected screenshot, trace, or HAR
  set stored as one short-lived non-publishable cache bundle for local secret
  review and exact-ID deletion.
- **Portability check**: fresh Chromium and Firefox/WebKit observations of the
  same closed profile-derived probe plan, producing only value-free facts and
  fixed diagnostics without locator rewrites.
- **Draft specification**: explicit author intent for parameters, macro
  sequence, side effects, and confirmation policy. Evidence may support
  locators and outputs but cannot invent action semantics.
- **Draft profile**: a typed generated or hand-authored profile candidate that
  must pass schema validation and fixture evidence gates before use.
- **Review bundle**: typed profile plus exact profile/evidence digests,
  assessment time, decisions, validation/revalidation reports, confidence,
  expiry, side-effect assessment, and unresolved gaps.
- **Capability bundle**: the canonical publication unit containing one exact
  reviewed profile release, normalized evidence, optional inert UWS
  companions, license/provenance, and Evidence-owned content/lifecycle
  descriptors. It is data, not a driver or browser session.
- **Static registry**: a canonical `index.json` plus immutable
  `blobs/sha256/<hex>` capability bundles. Publication is a local repository
  transaction; distribution is read-only static HTTPS.
- **Revalidation**: a non-secret, non-side-effect check that confirms profile
  locators, origins, and output extraction still match the target UI.
- **API wrapper split**: if a team builds a stable HTTP wrapper around browser
  scraping, OpenAPI describes that wrapper service. The browser profile
  describes the private UI binding behind the wrapper.

## Primary Workflows

1. Capture or import UI evidence from a browser session, crawler, or extractor.
2. Normalize evidence into prompt-safe, secret-free records.
3. Combine evidence with an explicit draft specification for actions,
   parameters, accessibility locators, waits, outputs, side effects,
   confirmation policy, confidence, and expiry.
4. Validate draft profiles against UWS browser-profile JSON Schema.
5. Produce review bundles for human or policy review.
6. Revalidate reviewed profiles without storing session secrets or committing
   side effects.
7. Verify bundle digests and freshness, then export browser-profile artifacts
   for UWS packages and OpenUdon authoring.
8. Optionally cache caller-supplied experiences and derived artifacts in an
   explicit private, content-addressed local store with expiry and pruning.
9. Promote only reviewed, current, secret-free derived artifacts into a
   deterministic capability bundle; raw cache content is never promotable.
10. Optionally help a downstream wrapper service align its response schema with
    the same reviewed extraction schema; OpenAPI for that wrapper remains owned
    by API tooling and the wrapper project.
11. Draft, validate, review, and locally discover package-owned browser
    authentication recipes for downstream trusted runtimes.
12. Optionally use a deterministic terminal guide to bind explicit capability
    intent and ambiguity decisions to reviewed normalized evidence.
13. Explicitly check selected profile actions against a current page using
    value-free locator, wait, and output-shape observations without executing
    any profile macro.
14. Explicitly observe selected authentication alternatives in independent
    headed ephemeral contexts, with exact origin approval and step-scoped POST
    ceilings, then emit one local value-free profile/review bundle only after
    all contexts close.
15. Optionally retain an explicitly selected screenshot/trace/HAR set as one
    bounded private bundle, or compare the same reviewed read-only profile
    probes across explicitly installed engines.
16. Explicitly keep one headed Chromium context alive while a human signs in,
    then explore toward a reviewed typed goal using Browsertools-issued
    candidates, per-action approvals, reduced observations, and no session
    export.
17. Produce a private deterministic authenticated-authoring candidate, then
    let OpenUdon independently validate and stage only canonical UWS profiles
    and existing safe review metadata for later trusted replay.
18. Treat every reduced observation as a finite authority generation, publish
    its complete portable context inventory, revalidate current accessible
    semantics before an action, and preserve the complete reviewed exploration
    trace separately from authentication success.
19. Record the exact MFA path actually exercised and optionally promote a
    bounded, sorted set of reviewed string/integer/number/Boolean/presence
    outputs without exposing their runtime values.
20. Serve the same author-session implementation through the standalone
    Browsertools CLI or an embedding executable's isolated worker process.
21. Explicitly supply reviewed browser-profile contracts to UWS 1.9.1
    content-trust analysis when a caller requests an advisory report.

## Scope

- Local schema validation and normalization for UWS browser-profile documents.
- An explicit, deterministic browser-profile resolver for UWS 1.9.1 advisory
  content-trust analysis, separate from validation and execution.
- Local-only validation, deterministic drafting, digest-bound review, expiry,
  and discovery for UWS browser authentication profiles.
- Offline validation, deterministic explicit drafting, digest-bound review,
  and expiry for package-local UWS browser registration profiles.
- Evidence records for accessibility targets, origins, outputs, fallback CSS,
  side effects, confirmation needs, confidence, expiry, and revalidation.
- Adapter interfaces for Playwright, llm-scraper, Crawl4AI, and Firecrawl
  outputs.
- Deterministic profile draft builders and repair helpers.
- Digest-bound review bundle generation, promotion verification, and
  redaction.
- Offline CLI commands for evidence import, drafting, validation, review, and
  fixture revalidation.
- An isolated, pinned Playwright-Go acquisition package and offline doctor;
  live capture commands must retain explicit origin, privacy, and lifecycle
  controls.
- A UI-safe doctor projection that never contains browser executables or
  private paths, while the standalone local CLI retains complete diagnostics.
- Explicit disclosure that accessibility-label reduction is heuristic rather
  than DLP; ordinary names, identifiers, and order numbers may remain in
  reviewed observations and traces.
- Headless, non-interactive Chromium capture with exact origins, GET/HEAD-only
  routing, ephemeral context destruction, closed resource/activity policy, and
  finite time/count/byte/depth/retention bounds. Raw ARIA/JSON-LD stays in the
  private cache until explicit review and redaction.
- Deterministic guided-authoring bundles containing the accepted spec,
  action-bound normalized evidence, ambiguity decisions, schema-valid profile,
  and promotable digest-bound review.
- Selected-action Chromium live checks that reuse the capture boundary, execute
  no portable macro, serialize no raw fixture, and report only declared paths,
  match counts, navigation-state reachability, and JSON types.
- Headed Chromium authentication observation driven only by validated profile
  steps: the operator supplies credentials and MFA in-browser, POST permission
  is bounded per exact step, and the atomically created private output contains
  no page or session material.
- Chromium-first authenticated goal authoring through a strict local NDJSON
  author-session protocol, with human credential/MFA entry, exact-origin and
  bounded POST authority, disclosure-gated reduced semantics, typed goal
  predicates, human completion, and atomic private results.
- A reusable `authorworker` process-entry package shared by the Browsertools
  CLI and a separately re-executed iCoT worker; it is not an in-process browser
  service for an authoring engine or HTTP handler.
- Popup and frame authoring through the reviewed UWS browser 1.6 and browser
  authentication 1.1 context contracts once those immutable schemas are
  available; main-only output continues to use the oldest sufficient version.
- Chromium rich capture with one-to-three explicit screenshot/trace/HAR
  members, a process-clock manifest, one-hour default/24-hour maximum
  retention, mandatory secret review, no promotion path, and confirmed
  exact-ID deletion.
- Chromium-baseline Firefox/WebKit portability checks in fresh contexts using
  the exact same profile-derived probes, with fixed value-free diagnostics and
  no locator rewriting or silent engine fallback.
- Private local cache APIs and CLI commands with explicit roots, retention,
  classification, and publication eligibility metadata.
- Deterministic capability bundle APIs, fixtures, and offline build/verify CLI
  commands, using `../evidence` for generic artifact/lifecycle records.
- Atomic local static-registry publication, bounded local/HTTPS search/pull/
  verification, and mixed-root browser source discovery for OpenUdon.
- Synthetic and fixture-based tests using non-real targets such as
  `https://example.test`.
- Downstream integration points for OpenUdon and browser runtimes.

## Non-Goals

- UWS wire schema ownership; that remains in `../uws`.
- API-source discovery, OpenAPI inventories, and provider catalog curation;
  those remain in `../apitools`.
- Live credential resolution, retained cookie/session storage, automatic
  CAPTCHA/MFA execution, account selection, persistent browser profile
  management, or production browser execution.
- Browsertools registering an account, submitting a registration form,
  resolving registration credentials, handling CAPTCHA/email verification/MFA
  responses, approving a registration run, reconciling duplicates or
  ambiguous outcomes, retaining account identifiers, or performing cleanup.
- Browsertools typing credentials, answering MFA, accepting credential
  environment-variable bindings, exporting an authenticated context, or
  resuming one after the author-session process exits. Browsertools may focus
  a candidate field or execute a separately approved candidate click without
  reading input values.
- Implicit browser launch, uploading cache content, or treating a private raw
  capture as publishable.
- A membership service, account system, catalog database, remote publication
  API, or custom moderation/reputation/billing layer.
- Static-registry publication of browser authentication profiles.
- Static-registry publication of browser registration profiles or their review
  bundles.
- A general Playwright/Puppeteer/WebDriver command language.
- Portable screenshots, traces, HAR, engine-specific selectors, implicit
  browser fallback, or ad hoc `browser.1.5` extensions.
- Arbitrary JavaScript execution inside portable profiles.
- Sending raw page text, DOM, ARIA snapshots, screenshots, request data,
  browser errors, or input values to an LLM; reduced page semantics require a
  once-per-run provider/model disclosure approval and have a human-only
  fallback.
- Pixel, coordinate, computer-vision, XPath, or DOM-path locators as portable
  action targets.
- Treating LLM extraction as trusted without deterministic validation and
  review.
- Scraping policy decisions such as ToS/robots interpretation, rate limits, or
  legal approval. Browsertools may record policy-review fields later, but it
  does not decide them.

## Product Posture

Browser profiles are intentionally weaker than official API contracts. Prefer
OpenAPI, Google Discovery, AWS Smithy, AsyncAPI, GraphQL, OpenRPC,
gRPC/protobuf, or OData when those sources cover the task. Use browsertools
when the useful capability is only exposed through a web UI and the resulting
profile can be reviewed before execution.
