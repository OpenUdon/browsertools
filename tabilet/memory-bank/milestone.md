## Status ID Pattern

Browsertools status files use one uppercase domain letter and a zero-padded
number from `01` through `99`:

```text
M01, M02, M03, ... M09, M10, ...
P01, P02, P03, ...
E01, E02, E03, ...
```

Task/status files use the lane ID:

```text
tabilet/memory-bank/status-M01.md
tabilet/memory-bank/status-M02.md
```

Lane meanings:

- `M`: completed legacy history and future cross-cutting public contracts.
- `P`: browser-profile validation, draft generation, review bundles, and
  portable artifact behavior.
- `E`: normalized evidence, adapters, capture/revalidation contracts, and
  trust-boundary hardening.
- `A`: additive browser authentication and registration profile authoring and
  review.

Do not reuse IDs after a status file exists. Keep cancelled files with `[X]`
rows, never create aggregate `status.md`, and do not reclassify completed M
history. Lane letters classify ownership rather than execution order.

Independent P and E milestones may proceed together only with explicit
non-overlapping files, resolved prerequisites, and downstream impacts. Shared
public contracts remain in M or name their cross-lane dependencies. Prefer one
active implementation milestone per lane.

### E03 Safe Chromium Live Capture

**Goal.** Acquire accessibility-first evidence from an explicitly selected

  credentials.

**Goal.** Guide an operator from bounded evidence to an explicit draft and

  confirmation, expiry, and ambiguity decisions; it never infers a mutation.

  shapes against the same origin-bounded ephemeral acquisition contract.
- Generated specs, profiles, evidence, decisions, and reviews pass the

  the same accepted answers and evidence.

  JavaScript, or expose a general browser command DSL.

### A02 Assisted Authentication Profile Capture

**Goal.** Let an operator manually complete sign-in and MFA in a headed,
ephemeral browser while Browsertools records only secret-free recipe evidence.

Acceptance:

- Browsertools never accepts credential environment-variable names or values,
  types credentials, answers MFA, reads cookies/storage, or exports storage
  state; the operator interacts directly with the headed browser.
- Exact login, challenge, and success origins are approved before navigation;
  unexpected origins, popups, downloads, permissions, and side-effectful
  non-authentication actions fail closed.
- The operator explicitly selects credential-slot locators, MFA alternatives,
  submit steps, and success evidence; secret scanning/redaction runs before
  any authentication draft or review artifact is written.
- Current-page locator/success checks reuse P03's value-free reporting shape;
  input values are never inspected, and authentication observation cannot
  accept caller-supplied Playwright selectors or probes.
- Closing or failing the session destroys the context. Output is a local
  `uws.browser-authentication.1.0` draft/review, never a session artifact or
  registry entry.
- Every selected alternative uses a separate context; only declared
  accessibility match counts and exact origins cross the browser boundary.
  POST is blocked except under an explicit finite ceiling for the active
  authored authentication step, and all other mutating methods stay blocked.
- The process clock supplies evidence time. The final exact-verifiable bundle
  is atomically created as a new `0600` file only after every context closes;
  stdin carries empty-line control signals and stdout carries no artifact.

Acceptance:

  storage, size/time retention, secret review, and deletion controls; none is
  publication eligible by default.
- Firefox and WebKit runs compare the same reviewed read-only capability
  against Chromium and produce diagnostics rather than silently rewriting
  locators.
- Popup, iframe, download, upload, permission, and visual-interaction pressure
  is recorded as supported-private, deferred, or a concrete browser.1.6
  proposal; Browsertools does not widen browser.1.5 ad hoc.
- Rich/cross-browser acquisition remains read-only and cannot reuse A02's
  authentication contexts, operator interaction windows, or POST ceilings.
- Default verification remains synthetic/offline, and rich or cross-browser
  integration suites require explicit installed-engine gates.
